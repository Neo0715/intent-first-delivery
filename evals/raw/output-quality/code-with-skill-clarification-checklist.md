## 1. 任务定位（先定场景，再定问题）

| 判定 | 结果 | 影响 |
|---|---|---|
| 代码场景 / 非代码场景 | **代码场景** | 先取证再下结论；本轮取证受阻（见「取证记录」） |
| 体量档位 | **第二档：小改动** | ①→③ 照走，产物放在对话里，不落成正式文档 |
| 是否**微小改动**豁免 | **否** | 跨多文件、要选型，一句话说不清 diff |
| 是否不可逆操作 | **否**（但含「大范围替换 print」这种难回退的批量改动） | 执行前先确认改动范围 |
| 用户是否说过「上次做的不是我想要的」 | 否（未提及） | 不因此强制走全流程 |

**为什么不是一档**：一句话说不清 diff —— 「到处 print」的「到处」= 改多少个文件、改成什么形态，都还没定。

**为什么不是三档**：这是一次性重构，读者只有用户自己，不需要 PRD 和正式交付文档。

## 2. 歧义清单

> 分类：**问用户** / **查资料** / **需实测验证** / **可合理假设**

| # | 模糊点 | 分类 | 为什么要紧 | 状态 |
|---|---|---|---|---|
| 1 | 「这个项目」**是哪个目录**？ | 问用户 | 它是空目录、没有任何代码，我读不到事实也无法取证 | 待处理 |
| 2 | 语言/技术栈（Python / JS-TS / Java / Go / C#） | 问用户 | 决定用哪套生态；`logging` vs `winston`/`pino` vs `slf4j` 完全不同 | 待处理 |
| 3 | 统一封装要做到什么程度 | 问用户 | 自写 30 行 wrapper ≈ 半天；结构化+落盘+轮转+上报 ≈ 几天。**这是最大的成本分叉** | 待处理 |
| 4 | 输出形态：控制台格式、是否写文件、是否结构化 JSON | 问用户 | 影响接口设计和是否要引入依赖 | 待处理 |
| 5 | 是否需要日志级别（DEBUG/INFO/WARN/ERROR）与可调开关 | 问用户 | 决定接口是 `log(msg)` 还是 `log.info(msg)` | 待处理 |
| 6 | 是否允许引入第三方依赖 | 问用户 | 有些项目硬性要求零依赖 | 待处理 |
| 7 | 调用方式是否要兼容现有 `print`（能直接搜替、还是要手改语义） | 问用户 | 决定改动量与是否引入语法级差异 | 待处理 |
| 8 | 现有 `print` 里是否混了「给用户的正常输出」（CLI 结果），不能都当日志 | **需实测验证** | 误把业务输出改成日志会改变程序对用户的行为 —— 这是最容易埋雷的一处 | 待处理（取证受阻） |
| 9 | 日志是否需要带上下文（模块名、函数名、行号、请求 ID） | 问用户 | 影响封装设计 | 待处理 |
| 10 | 是否需要保留原有输出文本/顺序（有人靠 grep 日志） | 可合理假设 → **默认保留** | 猜错代价低，先按保留做并声明 | 已列假设 |
| 11 | 敏感信息（路径、token）是否需要脱敏 | 可合理假设 → **默认不额外做**，只保留原有内容 | 主动加脱敏会改变输出 | 已列假设 |
