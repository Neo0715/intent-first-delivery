# 触发评测（trigger evals）

目的：验证 `SKILL.md` 的 `description` 在该触发时触发、不该触发时不触发。

方法、阈值、划分比例、迭代上限全部照 [agentskills.io/skill-creation/optimizing-descriptions](https://agentskills.io/skill-creation/optimizing-descriptions) 执行：

- 每条查询跑 **3 次独立试次**，算触发率；触发率 ≥ 0.5 判为「触发」
- 迭代集固定划分：**train 13 条 / validation 9 条**（各含比例相当的正负例），改描述只看 train，validation 只用来验收
- 迭代上限 5 轮；最终版本按 **validation 通过率**选，而不是按最后一轮选

## 三套查询集（口径不同，别混用）

| 集合 | 文件 | 构成 | 能证明什么 |
|---|---|---|---|
| **迭代集** | `trigger_queries.json` | 22 条：10 该触发 / 12 不该 | v1–v6 就是对着它迭代的。**不能当泛化证据。** |
| **回归集** | `regression_queries.json` | 12 条：T11–T14 该触发 / N13–N20 不该 | **原 `fresh_queries.json`**。因为 v5→v6 的改动理由**引用了其中的 N14**，它已不满足「未参与优化」，故改标为回归集，**只用于防止回退**。 |
| **泛化集** | `generalization_queries.json` | 10 条：G1–G5 该触发 / G6–G10 不该 | **本版新写**，只跑过这一轮。包内可核实：G1–G10 不出现在 v1–v6 任何一轮的判定材料里；「新写、未用于改动」是过程声明，见 `final-report.md` 第 3 节。用来验收 v6 是否真泛化。 |

> ⚠️ **泛化集是一次性的。** 一旦用它改过 `description`，它就不再「未参与优化」，必须另写一批新的。
> 另注：「本版新写」是过程声明——包内只能证明这 10 条没出现在 v1–v6 任何一轮的判定材料里。
> **任何后续改动 `description` 之后，本节结论作废，需重跑。**

## 判定方式

本环境没有 `claude -p` 那样的非交互跑批入口，所以用**全新上下文的 subagent** 充当触发判定器：
它只看到技能目录里的 `name` + `description`（外加一个无关技能作干扰项），看不到技能正文，
然后对每条消息独立判 3 次。判据就是官方那句话——*这条消息是否必须先澄清意图 / 先定验收标准 / 先取证才能保证做对*。

判定器看不到正文，所以它测的是**描述本身**的判别力，这正是要测的东西。

**口径必须说清**：这是**描述分类的代理指标，不是真实端到端触发率**，也不是触发率的**下界**。
判定器的唯一杠杆是「要不要加载这个技能」，而真实 agent 可能不加载就直接开始干活。
本环境没有可编程的 agent 运行器，测不了真实触发率，所以不声称测了。

## 负例怎么选

官方原话：最有价值的负例是 **near-miss（近义误触发）**，「写个斐波那契函数」那种测不出东西。
所以负例里有一半是刻意贴着脸设计的：

| 负例 | 为什么容易误触发 |
|---|---|
| N1 改一行错别字 | 也是「改东西」，但改法唯一 |
| N2 改第 8 行变量名 | 同上，且需要定位 |
| N5 改配置 + 重启 | 有两个动作，像是「任务」 |
| N6 改远程 README，内容已给定 | 涉及外部仓库、交付方式未定，最像需要澄清 |
| N9 删掉一批 `.tmp` | **不可逆操作**——最容易误判为必须走门禁 |
| G9 删掉超 7 天的 `.log` | **不可逆 + 范围写得极明确**——专测「不可逆」会不会压过硬性范围限定 |
| G10 去掉所有 `console.log` | **批量但完全可逆**——专测「批量」这一类会不会误触发 |

N9 / N13 / G9（不可逆删除）是**刻意保留的已接受偏差**，理由见 `final-report.md` 第 6.1 节。
N6 / N10 / N14 / G10 属**原因未定 / 待复测**，见第 6.2 节。

## 迭代记录

| 迭代 | 改了什么 | 结果 |
|---|---|---|
| v1 | 初版：强调「要产出东西就得走流程」+ 列举触发情形 | 作者记录 12/13 train、7/9 valid（N6 误触发）。⚠ 无原始输出 |
| v2 | 针对 v1 的 N6 误触发，补「用户已给全就照做」 | 作者记录 13/13、8/9。⚠ v2 validation 文件与 v1 逐字节相同，不可信 |
| v3 | 换判据为「还有没有必须靠猜才能定的决定」 | 作者记录 13/13、7/9。⚠ 无原始输出 |
| v4 | 「先取证」改成不能当动作执行的门禁，并点明「目标 ≠ 标准」 | **21/22**（train 13/13、valid 8/9，仅 N9）✅ `raw/v4/` |
| v5 | 审计后修订：补「探索不是后门」+「批量/不可逆操作默认问法」 | 迭代 21/22（N9）、回归 10/12（N13+N14）✅ |
| **v6（发布）** | 「批量或不可逆」收紧为「不可逆」 | 迭代 **19 / 20 / 22**（三轮）、回归 10/12、泛化 8/10 ✅ |

> ⚠ **证据边界**：可独立复核的只有 `raw/` 下已归档的几轮（v4 的 4 份、v5 一轮、v6 三轮 + 泛化一轮）。
> v1/v2/v3 的分数**不可独立复核**——磁盘上 v2 的 validation 文件与 v1 逐字节相同（MD5 一致），
> 是数据完整性错误；v1/v3 的原始输出不在包内。所以上表 v1–v3 三行是「作者的记录」，不构成本报告结论依据。
> `raw/descriptions.txt` 只保留了 v4 / v5 / v6 原文（v4 由判定提示词逐字提取），v1–v3 原文未归档。

**只看 train 会误判收敛**：v2 把 train 打到 13/13，validation 却掉分，且它新引入的边界句造成一处漏触发（T4）。
这正是官方要求划分 train/validation 的原因。

**只看总分不够，要看失败项落在哪条用例上**，而且要**看同一版本多轮之间稳不稳**：
v6 跑了三轮，N6/N9/N10 都在轮次间翻转过。所以「19 还是 22」这种总分差异本身说明不了太多，
要看「哪些项在多轮里稳定误触发」。多轮对比用 `tools/variance.mjs`。

## 结论（当前发布版 = v6，467 字符）

| 评测集 | 通过率 | 召回率 | 特异度 | 误触发 |
|---|---|---|---|---|
| 迭代集（第 1 轮） | **19/22 = 86.4%** | 100% (10/10) | 75% (9/12) | N6、N9、N10 |
| 迭代集（第 2 轮） | **20/22 = 90.9%** | 100% (10/10) | 83% (10/12) | N6、N9 |
| 迭代集（第 3 轮） | **22/22 = 100%** | 100% (10/10) | 100% (12/12) | — |
| 回归集 | **10/12 = 83.3%** | 100% (4/4) | 75% (6/8) | N13、N14 |
| 泛化集 | **8/10 = 80.0%** | 100% (5/5) | 60% (3/5) | G9、G10 |

- **在这几轮里，正例每一轮都全部触发**——这是本代理指标下的一条观测事实，
  **不等于真实召回率，也不是触发率下界**。
- 失败项分两类，逐条理由见 `final-report.md`：
  - **已接受的偏差**（有意保守）：N9、N13、G9，全属不可逆删除，代价只是一句确认。
  - **原因未定 / 待复测**：N6、N10（轮次间翻转）、N14、G10（单轮内 3/3 误触发、无跨轮证据；且 v5→v6 的改动理由未被证据支持）。
- `audit-current.mjs` 会因「原因未定」那 4 条报 **`⚠ ATTENTION`**（exit 1）——**这是刻意如此**，
  工具不会因为某个失败 ID 在文档里被提到过就替它放行。
- 审计**逐集合各挑自己的主运行文件**：迭代集 / 回归集 → `raw/v6-raw.txt`（第 1 轮），
  泛化集 → `raw/gen-v6-raw.txt`。所以泛化集的 G9 / G10 也在审计范围内，
  汇总口径是 19/22 + 10/12 + 8/10 = **37/44**，**不是**拿三轮里最好的那轮来报数。

## 复跑方式

复跑只需要本包自身，不需要任何包外脚本或包外文件。工具都在 `evals/tools/` 里，
只依赖同包的 JSON（按脚本自身位置解析，全是相对路径）。

```bash
# 1. 把某版 description 写成纯文本 desc.txt（只放 description 的值，不要 frontmatter），放在 evals/ 下
# 2. 生成判定器提示词（第三个参数是逗号分隔的查询 id，省略 = 该集合全部）
node evals/tools/build-judge-prompt.mjs desc.txt out.md "T1,T4,N9"
#    批量生成（推荐，产物自包含、可归档）：
node evals/tools/build-prompts.mjs evals/generalization_queries.json v6 gen-v7
# 3. 把提示词交给一个全新上下文的 subagent 跑，把它的原始输出存成 raw.txt
# 4. 打分（三集合自动分流；试次不足会警告且不得视为通过）
node evals/tools/score.mjs raw.txt
```

每一步必须产出的文件：

| 步骤 | 输入 | 必须产出 |
|---|---|---|
| 1 | `SKILL.md` 里的 `description` 值 | `desc.txt`（纯文本，≤1024 字符） |
| 2 | `desc.txt` / 查询集 JSON | 判定器提示词（技能目录 + 待判消息 + 输出格式 + 落盘路径） |
| 3 | 提示词 | `raw.txt`（每条消息 3 行 `<ID> trialN: YES\|NO \| 理由`） |
| 4 | `raw.txt`（可多个） | 逐条明细表 + 分集合统计 + 试次完整性检查 |

**只有 validation（和泛化集）的通过率决定是否接受这一版描述**，train 只用于迭代。

## 回归审计：改完描述必须再跑这个

```bash
node evals/tools/audit-current.mjs .
```

它解决一个很容易出事、又完全看不出来的问题：**`score.mjs` 打的是「你递给它的那批输出」，
不是「现在 `SKILL.md` 里那一版描述」。** 只要在评测之后改过 `description`，
手上所有分数就悄悄不再描述实际会被加载的东西了——表面一片全绿，实际没测过新版。

它不做任何 API 调用，也不需要重跑：

1. 从 `SKILL.md` 读出当前生效的 `description`，算 SHA-256
2. 在 `raw/descriptions.txt` 里找这个哈希——没找到就报「这段文字没被评测过」
3. 找到后，用对应的原始输出文件重新算分
4. **试次完整性**：被覆盖的每个集合、每条查询都必须凑满 `runs_per_query` 次有效试次；
   有任何一条缺失 → 判 `TRIALS MISSING`，**不得 PASS**
5. 把失败项分成两类并**分开输出**：
   - **已接受偏差**——该 id 出现在 `final-report.md` 的**「已接受的偏差」小节**里（不是出现在文档任意位置）
   - **原因未定 / 待复测**——其余失败，一律算这一类
6. 若同一版本有多轮独立运行，额外报出运行间翻转的查询

退出码：`0` = 通过；`1` = 试次缺失或有未处置的失败项；`2` = 没匹配到任何记录。

**每次动过 `description`，跑一次这个。**

## 泛化检查

当前 `generalization_queries.json` 的 10 条（G1–G10）是本版新写的，**在 v6 定稿前没有出现在任何一轮
判定材料里**（这一条包内可核）；「新写」本身是过程声明，不能仅凭本包独立证明。
每条判 3 次，结果：

| 结果 | 明细 |
|---|---|
| 该触发 **5/5** ✅ | G1 投诉分类方案 · G2 补老系统文档 · G3 CI 太慢 · G4 竞品分析 · G5 备份脚本 |
| 不该触发 **3/5** | G6 改第 42 行端口 · G7 删 CSV 空行 · G8 useEffect 空依赖 |
| **误触发 2 条** | **G9**「删 `~/logs` 下超 7 天的 .log」3/3 YES；**G10**「去掉所有 `console.log`」3/3 YES |

合计 **8/10 = 80%**，召回 100%，特异度 60%。

- **G9** 是描述在**按设计工作**：范围虽明确，但删除不可逆，判定器按「不可逆的操作，哪怕范围看起来清楚……要当面确认」判的 → 已接受偏差。
- **G10** 与回归集的 **N14** 同族（批量、「所有」），本轮 3/3 误触发（**只有这一轮，无跨轮证据**）→ 原因未定 / 待复测。

> 泛化集只有 **一轮**（每条 3 试次），未做多轮复跑；上述结论以此一轮为限。
> ⚠️ **这批查询是一次性的。一旦用它们改过描述，本节结论作废，必须另写一批新的。**

## 规范合规的机械校验

```bash
node evals/tools/validate-spec.mjs .
```

不联网、不调 API，只按 `agentskills.io/specification` 的硬条款逐项查，**分三档**：

- **规范要求**：`name` 字符合法且与父目录名一致、`description` ≤1024、正文 <500 行、引用一层深且都真实存在
- **官方建议**：约 100 token 元数据、渐进披露等
- **本包自定义**：总文件数、整份 `SKILL.md` 行数

每档独立报 PASS/FAIL。发布版在正确命名的目录下应全绿；若目录名与 `name` 不一致
（如工作目录 `intent-first-delivery-v2`），那条会如实报 FAIL——这是校验器在干活，不是坏了。

**它查不了的东西**：正文写得清不清楚、`description` 的语义好不好、触发率高低——
前两条靠人读，第三条靠上文的触发评测。**改完 `description` 或正文结构，跑一次这个，再跑一次触发评测。**

## 措辞纪律（本版按审计要求收紧）

以下说法**不得出现**在任何结论里：

- ❌「误差 ±2」——19–22 只是**同版本 3 轮内的观测范围**，n=3，不是方差的统计估计。
- ❌「从不漏触发」／「召回率下界 100%」——「这几轮里正例全部触发」是观测事实，不等于真实召回率，更不是下界。
- ❌「v6 优于／劣于 v5」——v5 只有 1 轮、v6 有 3 轮，不足以把「描述改动」与「判定器噪声」分开。
- ❌「所有数字都能从包内证据复算」——只有 `raw/` 里已归档的那几轮可以；
  输出质量对照每格只跑了 1 次，v1–v3 无原始输出。
