# 澄清清单

> 阶段 ① 接收诉求 的产物。
> 用途：把所有模糊点摊开，逐条定位到具体答案，**并保证答案被折叠回产物**（而不是聊过就算）。
> **产出这份清单后必须停下来等用户确认。**

---

## 1. 任务定位（先定场景，再定问题）

| 判定 | 结果 | 影响 |
|---|---|---|
| 代码场景 / 非代码场景 | | 非代码场景 → 盘问到共识为止；代码场景 → 先取证再下结论 |
| 是否**微小改动**豁免（一句话可描述完） | 是 / 否 | 是 → 声明豁免理由后可直接执行 |
| 是否不可逆操作 | 是 / 否 | 是 → 必须确认，不许简化流程 |
| 用户是否说过「上次做的不是我想要的」 | 是 / 否 | 是 → 必须走全流程 |

---

## 2. 歧义清单

> 逐条列出**现在还不知道、但会影响结果**的点。不要只列你已经会问的。
> 分类的目的是决定「该问谁」还是「该自己查」。

| # | 模糊点 | 分类 | 为什么要紧 | 状态 |
|---|---|---|---|---|
| 1 | | 问用户 | | 待处理 |
| 2 | | 查资料 | | 待处理 |
| 3 | | 需实测验证 | | 待处理 |
| 4 | | 可合理假设 | | 待处理 |

**分类说明**：

- **问用户** —— 属于用户的业务事实、偏好、判定标准。**外部查不到，只能问。**
- **查资料** —— 客观事实，官方文档 / 源码能给出答案。**先自己查，查完再决定是否还要问。**
- **需实测验证** —— 「能不能跑通」「性能够不够」这类，光查资料定不了，必须真跑一遍。
- **可合理假设** —— 影响小、猜错代价低。**列为假设，写进意图契约，不要占用用户注意力。**

---

## 3. 提问

> 提问原则：一轮问透（≤3–5 条、同一主题），不要分批挤牙膏；不问显而易见的问题，只挖用户可能没考虑到的硬骨头。

**该问的**：

- 判定标准（**最重要**）：怎么算做对了？怎么算做砸了？
- 边界情况：什么情况下这个方案不适用？
- 失败态：出错了希望怎么表现？
- 谁用：只有你自己用，还是别人也要用？
- 优先级：哪部分先做，哪部分可以砍？

**不该问的**（问了是浪费用户时间）：

- 代码库里已经能查到的事实
- 官方文档里写明的用法
- 用户明显不关心、且猜错代价极低的细节

|---|---|---|---|---|

**折叠位置可选**：`intent-contract`（目标/边界/验收标准/假设）、`prd`（需求细节）、`implementation-plan`（技术约束）。

> ⚠️ **「折叠」是硬要求。** 只在对话里聊明白、没写进产物的答案，在后续步骤里等于不存在 —— agent 会忘，换 agent 更会忘。

## 4. 查证记录

> 先自己查，查不到再问。

| # | 待查事项 | 来源 | 结论 | 证据等级 |
|---|---|---|---|---|
| 1 | | 官方文档 / 源码 / 实测 / 二手 | | `[已验证]` `[未核实]` |

**证据等级定义**：

- `[已验证]` —— 一手来源或自己的实测输出，可直接引用
- `[未核实]` —— 仅有二手来源或推断，**不能作为结论使用**
- `[待用户确认]` —— 属于用户的业务事实

> **查不到就如实说查不到。** 严禁编造 API、参数、版本号、库名、性能数字或引用链接。
