# 排查简报

> 阶段 ① 接收诉求（代码场景）的产物。
> 核心原则：**根因 > 猜测**。禁止在未复现的情况下提出修复方案。
> 固定顺序：**复现 → 最小化 → 假设 → 插桩 → 修复 → 回归**

---

## 0. 现象

**用户描述的原话**：

```
（原文粘贴，不要改写）
```

**实际报错原文**（一字不改地粘贴，不要转述）：

```
（原始报错 / 日志 / 堆栈）
```

**拿不到报错原文时**（用户只给了症状，例如「客户说导出来的文件打不开」）：**不要编，也不要留一个空着的必填项**。照下面这个格式写清楚「缺什么、怎么补」：

```
（用户未提供报错原文）
缺什么：原始报错字符串 / 日志 / 堆栈
为什么现在拿不到：<用户只描述了症状 / 没有权限 / 日志已轮转>
怎么补：<已向用户索取 / 需要哪台机器上的哪个文件 / 需要开哪个日志级别>
在本轮排查中先用什么替代：<用户原话 + 我实测复现出的错误，注明这是我复现的、不是他给的>
```

**替代品必须标明来源**：我复现出来的报错是我复现的，不能冒充「用户的原始报错」。这条区分直接决定后面假设的方向对不对。

> ⚠️ 报错原文是最重要的资产。转述会丢掉关键字符串，而那个字符串往往是唯一的线索。

**环境**：OS / 运行时版本 / 依赖版本 / 分支 / commit

## 1. 复现

| 项 | 内容 |
|---|---|
| 复现步骤 | 1. <br>2. <br>3. |
| 复现率 | 必现 / 偶发（约 __ 次中 __ 次） |
| 是否在我这里复现 | 是 / 否 |
| 数据 / 前置状态 | |

**复现不了怎么办**：不要猜。先解决「为什么复现不了」—— 环境差异？数据差异？时序差异？只有偶发才出现？把「无法复现」本身当成第一个待解问题。

> 不稳定的偶发问题优先查并发、缓存、时序、外部依赖超时，而不是业务逻辑。

| 项 | 内容 |
|---|---|
| 剥离掉的部分 | |
| 最小复现单元 | 单文件 / 单个函数 / 单条命令 |
| 最小复现命令 | |

> 最小化的价值：把「哪一部分导致问题」从猜测变成排除法。最小化后仍复现，说明范围已经锁定。

## 3. 假设

> 每条假设都必须写出「**如果它成立，我应该能观察到什么**」。观察不到的假设就是猜测，不许进入插桩。

| # | 假设 | 若成立，应观察到 | 验证方式 | 结果 |
|---|---|---|---|---|
| 1 | | | | 成立 / **被推翻** |
| 2 | | | | |

**被推翻的假设也要记录**，并写清「为什么被推翻」—— 否则下一个人会重新提一遍。

| # | 插了什么 | 位置 | 观察到什么 | 支持/推翻了哪个假设 |
|---|---|---|---|---|
| 1 | | file:line | | |

**插桩手段**：日志 / 断点 / 断言 / 二分注释 / 打印中间值 / 抓包

> 假设被推翻 → **回到第 3 步重新假设**。不要将就着修一个已经被推翻的方向。

> 

**为什么这是根因而不是症状**（说明因果链）：

> 

**证据链**：现象 → 最小复现 → 假设 → 插桩观察 → 根因，每一环都可追溯。

## 6. 修复

| 项 | 内容 |
|---|---|
| 改动文件 | file:line |
| 改动说明 | |
| 是否偏离原定范围 | 是（记录偏离原因） / 否 |
| 是否压症状 | 是 → **停下，这不是修复** / 否 |

> **严禁把症状压掉当成修复**：catch 住异常不处理、加个 `if` 绕过、调大超时、重启了事、注释掉报错。
> 压症状会让问题在别处以更贵的形式回来。区分标准：**症状消失但因果链没断 = 压症状。**

---

## 7. 回归

| 项 | 内容 |
|---|---|
| 原问题是否消失 | 是 / 否 |
| 复现步骤重跑结果 | |
| 新增测试 | 测试文件:line（**修复前应先写出失败测试**） |
| 相关测试套件 | 通过 / 失败 |
| 是否引入新问题 | 否 / 是（列出） |
| 回归判定 | `已验证` / `部分验证` / `失败` / `未验证` |

**回归判定说明**：

- `已验证` —— 验证项全部跑通
- `部分验证` —— 有环境或数据缺失没跑完，需补齐后重验
- `失败` —— 发现残留问题，带着这个证据回到第 3 步重新排查

> ⚠️ **测试套件全绿不等于修好了。** 如果原始复现步骤从未被真正执行过，那就不算验证通过。
